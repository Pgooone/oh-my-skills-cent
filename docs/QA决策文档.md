## 0. 本轮背景

| 项 | 内容 |
| --- | --- |
| 原始需求 | 基于 oh-my-skills 新增**工作流管理器**：用户不仅下载单个 skill，还能使用多 skill 编排的工作流；AI agent 可直接读取工作流并下载相应 skill 执行整条流程 |
| 本轮新变量 | ① fork 上游为独立项目 **oh-my-skills-cent**（https://github.com/Pgooone/oh-my-skills-cent）② 原项目只支持 macOS/Windows 桌面，要求**可在 Linux 服务器部署** |
| 事实纠正 | 用户最初认为「原项目只能在 macOS 上运行」——源码事实：README 与 CI 显示官方支持 macOS（dmg）+ Windows（NSIS），**缺的是 Linux**；打包目标 `["app","dmg"]`，CI 矩阵只有 macos-latest / windows-latest |

## 1. 源码事实基础（拷问的输入）

对 fork 后源码（`Oh-My-Skills-源码/`）的实际勘察结论：

| 事实 | 证据 | 对决策的影响 |
| --- | --- | --- |
| Rust 后端约 5.5k 行，模块清晰 | `src-tauri/src/`：commands / fs_ops / models / registry / scanner / settings / sync_plan | 业务逻辑可整体复用 |
| Rust 核心与 Tauri 耦合极浅 | 全库 `tauri::` 引用仅 7 处，其中 4 处是 `AppHandle`（路径解析），3 处在 lib.rs 入口 | Web 壳改造不需要重写核心 |
| 前端已有「非 Tauri 环境」分支 | `src/lib/runtime.ts` 的 `isTauriRuntime()`；所有 `invoke()` 集中在 `App.tsx` 且逐个有守卫；存在 `demoData.ts` 兜底 | invoke → fetch 的替换点集中，前端基本同构 |
| 前端仅用 2 个 Tauri 插件 | `plugin-dialog`（目录选择/确认框）与 `plugin-opener`（open_path 打开文件管理器 / open_url 限 github.com）；未使用 updater/fs/window/store 等任何其他 Tauri API | Web 版需要替代的桌面 UI 能力仅这两处 |
| 无任何 macOS 专有编译分支 | 全库无 `cfg(target_os="macos")`；仅 `fs_ops.rs`（symlink）与 `registry.rs`（CLI/App 检测路径）存在 `#[cfg(unix)]` / `#[cfg(windows)]` 二分支，且都有 `not(windows)` 兜底——Linux 走 unix 分支天然兼容，symlink 在 Linux 原生支持；无任何平台专有 crate | Linux 适配只需补检测路径，不动核心逻辑 |
| 前后端契约是 19 个 command | `lib.rs:13-33` 注册；前端实际调用其中 14 个，全部是「参数 → serde JSON 返回」形态，无流式、无事件 | 1:1 映射 HTTP endpoint 即可，无协议转换成本 |
| 平台差异在配置文件 | `tauri.macos.conf.json` / `tauri.windows.conf.json`，无 linux 配置 | Linux 桌面构建也未做过 |
| Agent skills 目录是 home 相对路径 | `registry.rs`：`~/.claude/skills` 等，经 `home_dir()` 展开 | Linux 上天然成立，无需改路径表 |
| Agent 可执行文件检测有 Windows 专有路径 | `registry.rs:821-955`：`~\AppData\...` 系列 | Linux 版需补 PATH 检测（工作项，非决策） |
| 中心库是纯本地目录 | 默认 `~/.oh-my-skills/skills`（`settings.rs`），非 git 仓库、非远程 API | Web 平移无语义障碍 |
| 全部状态为 JSON 文件，无数据库 | `app_data_dir` 下：settings.json / inventory-cache.json / plans/ / sync-history.json / backups/（Linux 对应 `~/.local/share/...`） | Web 版以数据目录配置（如 `OMS_DATA_DIR`）替代 Tauri 的 app_data_dir 解析 |
| 更新检查 = git clone + 目录哈希对比 | `commands.rs:349-407`：`git clone --depth 1`（系统 git CLI，仅限 GitHub 域名）→ SHA-256 对比 | 单二进制运行时需要服务器装有 git |

## 3. 逐题完整问答记录

### Q1 · 部署目标形态

**问题背景**：用户提出「原项目只能在 macOS 上运行，想让其可以在 Linux 服务器部署或者 Docker 中部署」。Tauri 桌面应用无法运行在无图形界面的服务器上，所以「服务器部署」的读法直接决定整个架构走向。这是第一根承重墙。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **Web 应用（推荐）** | Rust 核心逻辑抽出来改成 HTTP 服务，React 前端走浏览器访问，服务器上跑一个进程即可 |
| 仅 Linux 桌面 GUI | 给 Tauri 加 Linux 桌面构建（deb/AppImage），仍是有显示器的桌面软件——与「服务器/Docker」语境不匹配 |
| 两者都要 | 桌面版（含 Linux GUI）与服务器 Web 版并行演进，工作量最大 |

**推荐理由**：「Linux 服务器 + Docker」语境下服务器通常无图形界面，桌面 GUI 读法不成立；Web 应用是唯一自洽的解读，且源码勘察显示改造成本低（见 §1）。

**✅ 最终选择：Web 应用**

---

### Q2 · 桌面版去留

**问题背景**：确定 Web 化后，原桌面版（macOS/Windows Tauri 应用）是保留还是抛弃。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **双形态：桌面 + Web（推荐）** | 保留 Tauri 桌面壳不动，新增 HTTP server 二进制；两个壳共享同一套 Rust 核心模块；上游同步能力保留 |
| Web-only 硬分叉 | 删掉 Tauri 壳变纯 Web 应用；代码更简，但与上游彻底分道，无法合并上游更新，失去桌面体验 |

**推荐理由**：① Rust 核心与 Tauri 耦合极浅（仅 4 处 `AppHandle`），抽共享核心成本低；② 前端已有 `isTauriRuntime()` 分支，天然支持双运行时；③ 保留桌面壳 = 保留与上游同步的可能性；④ 用户日常开发机（macOS/Windows）仍可能用桌面版。

**✅ 最终选择：双形态：桌面 + Web**

---

### Q3 · 服务器语义

**问题背景**：原产品管理的是「**本机** AI 工具的 skills 目录」。搬到服务器后，「本机」指谁？这决定产品本质是否改变。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **单机语义平移（推荐）** | agent 工具装在服务器上（云开发机/远程环境），Web UI 管理服务器本机目录。产品语义不变，只是 UI 入口从桌面窗口变成浏览器。单用户、无多租户 |
| 团队共享中心库 | 服务器变成团队 skill 中心库/注册表服务，成员各自拉取——需要同步协议、权限、多用户，产品形态大变、范围爆炸 |
| 远程管理多机 | 一个 Web 服务管理多台机器的 agent 目录——需要远程执行/SSH/agent 上报，复杂度最高 |

**推荐理由**：原项目是单机工具，「平移」保持全部已有架构与心智模型成立；另外两个选项本质上是做一个新产品。

**✅ 最终选择：单机语义平移**

---

### Q4 · Docker 目录方案（范围变更）

**问题背景**：Docker 容器有隔离的文件系统，默认看不到宿主机上的 agent skills 目录，需要确定目录从哪来。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **卷挂载宿主目录（推荐）** | 镜像只含 Web 服务，`docker run -v ~/.claude:/data/claude` 映射进容器；镜像小、通用 |
| 全包含 agent 工具 | 镜像内预装 agent CLI + Web 服务，做「开箱即用的云端开发环境盒」；镜像重、维护成本高 |
| 轻量为主、全包为示例 | 官方只发轻量镜像，全包作为可选示例 Dockerfile |

**✅ 最终选择：「算了，先不做 Docker 版本的」** —— 用户直接将 Docker 移出 v1 范围。

**备注**：这是本轮唯一的范围砍除决策。Web 应用形态不变，部署方式转为 Linux 服务器直接部署（引出 Q5）。Docker 化以后想做时，只是给单二进制套层壳，无返工。

---

### Q5 · 服务器交付形态

**问题背景**：不做 Docker 后，Web 版以什么形式交付到 Linux 服务器上跑起来。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **单二进制内嵌前端（推荐）** | 编译出一个自包含可执行文件（前端 HTML/JS/CSS 用 rust-embed 打进二进制），scp 到服务器直接 `./oh-my-skills-cent` 运行；服务器零依赖，类比「绿色免安装软件」；开机自启配 systemd |
| 前后端分开部署 | 服务器装 nginx 管前端静态文件 + 独立跑后端进程，需配置转发、管两个进程——对单人单服务器场景杀鸡用牛刀 |
| 源码构建运行 | 服务器装 Rust/Node 工具链从源码编译——开发模式不是部署方式 |

**推荐理由**：① 场景是「一个人、一台服务器、一个工具」，最朴素诉求是拷上去就能跑；② 符合项目「简单、零新增后端」精神；③ 反悔成本为零——以后想加 Docker 或 nginx 只是给二进制套壳；④ 与 Tauri 桌面版「一个安装包搞定一切」同一思路。

**✅ 最终选择：单二进制内嵌前端**

**备注**：用户初次选择后表示「不知道如何选择，请你说人话」，在获得通俗解释（绿色免安装软件类比、三选项部署流程对比）后**二次确认**仍选单二进制。

### Q6 · 访问控制（偏离推荐）

**问题背景**：Web 版能执行磁盘写入（Sync Plan），如果裸奔在公网等于开放远程文件操作。但产品语义是单用户（Q3）。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **可选 token + 默认本地（推荐）** | 默认监听 127.0.0.1；显式绑 0.0.0.0 时强制要求访问令牌。一个 middleware + 简单登录页，成本低 |
| 无认证，仅 localhost | 只监听 127.0.0.1，公网访问靠用户自己 SSH 隧道或反向代理加认证；最简单，但用户改绑 0.0.0.0 就裸奔 |
| 单用户账号密码 | 内置账号密码存配置文件，比 token 略重，体验差不多 |

**推荐理由（当时推荐 token 的理由）**：成本极低（一个中间件），但能封死「误绑公网」这个真实风险。

**✅ 最终选择：无认证，仅 localhost** —— 用户明确接受「改绑 0.0.0.0 即裸奔」的风险。

**备注**：为兜底该风险，产生护栏推导决策 D4（见 §4）：**程序绑到非 localhost 地址时拒绝启动并提示**——不开门比开门不锁安全。此题记录为 ADR-0008。

### Q7 · 上游跟随策略（偏离推荐）

**问题背景**：fork 出的 oh-my-skills-cent 与上游 nextcaicai/oh-my-skills 保持什么关系，决定仓库结构与改动侵入程度。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **跟随上游（推荐）** | 定期 merge upstream/main，改动最小侵入；但 Web 化与工作流是上游没有的大方向，长期必然产生合并冲突 |
| 独立产品线 | 不跟随上游，自由重构（如拆 Cargo workspace）；结构最干净，但上游修复全部要手动移植 |
| 选择性摘桃 | 大体独立演进，上游出现重要修复/功能时 cherry-pick；合入成本居中 |

**推荐理由（当时推荐跟随的理由）**：改动最小侵入时合并冲突最少。

**✅ 最终选择：选择性摘桃** —— 用户判断自己会更独立地演进。

**备注**：此选择直接导出推导决策 D1（仓库结构：核心模块文件路径不动，Web 服务作为同 crate 新二进制加入，保证摘桃可应用）。此题记录为 ADR-0007。

### Q8 · 原 5 个 ADR 复核

**问题背景**：第一轮 PRD 的 5 个架构决策，在双形态新架构下是否仍然成立。

| ADR | 原决策 | 本轮复核 |
| --- | --- | --- |
| 0001 | 工作流采用声明式模型（放弃可执行编排） | ✅ 维持 |
| 0002 | 本产品充当远程来源（官方公共 Git 仓库作默认注册表） | ✅ 维持；Web 模式下由服务器去拉 Git 仓库，语义一致 |
| 0003 | 「使用工作流」复用 Sync Plan | ✅ 维持；Sync Plan 在共享 Rust 核心，两个壳都能调用 |
| 0004 | 双输出形态（入口清单 + 打包 skill） | ✅ 维持 |
| 0005 | 工作流包 = 目录 + workflow.yaml + README，步骤引用不内联 | ✅ 维持 |

**✅ 最终选择：全部维持** —— 只补新决策，不翻旧账。

### Q9 · 官方注册表仓库

**问题背景**：第一轮 PRD 的开放问题之一是「官方公共仓库的具体地址与治理」。当时上游不归用户管，无法拍板；现在 fork 后注册表由用户自己定义，可以落地。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **独立注册表仓库（推荐）** | 新建 `Pgooone/oh-my-skills-workflows`：根 `index.json` + 各工作流子目录；治理=贡献走 fork+PR、用户个人审核；内置为默认 registry URL |
| 放主仓库内 | 注册表放 oh-my-skills-cent 的 `workflows/` 目录；简单但污染主仓库、clone 体积变大 |
| 暂无官方注册表 | v1 只做本地创建+使用，砍掉原 PRD v1 的「从官方仓库浏览下载」 |

**推荐理由**：独立仓库职责单一、主仓库干净；用户完全控制，治理流程（fork+PR+个人审核）与原 PRD 决策一致。

**✅ 最终选择：独立注册表仓库（Pgooone/oh-my-skills-workflows）**

**备注**：建议注册表仓库预置 2–3 个示例工作流（如「软件开发工作流」= 需求 grill → 记录 domain-modeling → 编程），上线即有内容可下载。

### Q10 · 打包 skill 合并策略

**问题背景**：第一轮 PRD 的开放问题之二。打包 skill 模式（ADR-0004 的双输出形态之一）要把多个被引用 skill 的内容打成一个自包含包，如何打？

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **结构化拷贝（推荐）** | 打包 skill = 目录：`SKILL.md` 只写工作流级编排说明（分组→步骤→每步该做什么），`skills/` 子目录放各被引用 skill 的完整拷贝；自包含可分发、不做文本合并、更新时整目录重新生成 |
| 文本内联 | 把各 skill 的 SKILL.md 全文合并进一个打包 SKILL.md；单文件但内容膨胀，源 skill 更新后打包版即过期 |
| 纯引用 | 只含编排说明+引用列表，依赖各 skill 独立安装；最轻但不自包含，与入口清单模式价值趋同 |

**推荐理由**：打包模式的独特价值是「便携分发」，必须自包含；结构化拷贝既自包含又避免文本合并的更新地狱（源 skill 更新 → 整目录重新生成打包即可）。

**✅ 最终选择：结构化拷贝** —— 记录为 ADR-0009。

### Q11 · 实施顺序

**问题背景**：两条工作线——Web 壳（平台迁移，本轮新增）与工作流管理器（第一轮 PRD 主线）——谁先谁后。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **Web 壳先行（推荐）** | 阶段一 = Web 壳（HTTP server + 单二进制 + Linux 部署文档）；阶段二 = 工作流 v1（原 PRD v1 范围）；阶段三 = 原 v2 |
| 工作流先行 | 先在桌面版做工作流 v1，Web 壳后做；服务器价值延后兑现 |
| 并行推进 | 两条线同时做；一个人精力有限，不推荐 |

**推荐理由**：① Web 壳工作量小（架构已有同构基础），先落地先验证；② 它是新架构的地基，地基先打；③ 先兑现「服务器上用 oh-my-skills」的价值；④ 工作流逻辑写在共享核心，两壳天然同时获得，不受壳先后影响。

**✅ 最终选择：Web 壳先行**

## 4. 推导决策（由拍板决策直接导出，无需单独拍板）

| # | 推导决策 | 导出依据 |
| --- | --- | --- |
| D1 | **仓库结构**：Web 服务作为 `src-tauri` 同 crate 的新二进制（如 `src/bin/oms-web.rs`）加入，核心模块文件（models/registry/scanner/sync_plan/fs_ops）**路径不动**；不拆 workspace | Q7 选择性摘桃 → 保持文件路径稳定，上游 patch 才能干净应用 |
| D2 | **Web 框架选型**：axum（HTTP）+ rust-embed（前端内嵌）；业务模块签名中的 `&AppHandle` 抽象为 `AppContext { data_dir, home_dir }`（机械性改动但触碰面广）；19 个 command 1:1 映射 HTTP endpoint | 技术默认项；axum 与 tokio/tower 生态和 Tauri 同源；深度分析确认 AppHandle 是业务层与 Tauri 的唯一耦合 |
| D3 | **Web 版桌面能力替代**：目录选择 → 服务器端目录浏览 API + 文本输入路径（`discover_project_workspaces` 可当校验接口）；`open_url` → 前端 `window.open`；`open_path` 改为「显示路径」；确认框 → 浏览器/自制 modal（`App.tsx` 已有降级分支） | 浏览器无原生文件对话框与「打开文件管理器」语义；前端仅有的 2 个 Tauri 插件即 dialog 与 opener |
| D4 | **无认证护栏**：绑定地址非 127.0.0.1 时拒绝启动并打印原因 | Q6 选了无认证 → 必须封死误绑公网的路径 |
| D5 | **一步多 skill 的顺序约定**：skills 数组有序，数组顺序即加载/执行顺序；显式写入入口清单 README 与打包 SKILL.md | 原 PRD 开放问题之四，由 ADR-0001（声明式有序）直接导出 |
| D6 | **Linux agent 检测**：补 PATH 查找方案（`which` / `~/.local/bin` / `/usr/local/bin`）；skills 目录表（`~/.claude/skills` 等 home 相对路径）无需改动；`/Applications/*.app` 类 macOS 检测在 Linux 上静默找不到、不报错，服务器场景 CLI 证据已够用 | §1 源码事实 + 深度分析确认 |
| D7 | **HTTP 层路径白名单**：所有接受路径参数的 endpoint 必须 jail 在「已注册的 agent skills 目录 + 中心库 + 数据目录」内——现 `remove_skill_entries` 仅靠「父目录名为 skills」防护，Web 化后路径来自 HTTP 请求，不设 jail 就是任意文件删除 API | 深度分析发现；即使仅 localhost 也应防御（防误操作与前端 bug 放大） |
| D7-R1 | **D7 分层修订（批次 2 验收时发现）**：严格 jail 只适用「文件变更类」操作（remove_skill_entries / update_skills_sh_skill / apply_sync_plan）；「注册/浏览类」操作（list_dir / discover_project_workspaces.basePath / save_settings.libraryPath）改用宽松规则（home 子树 + 已注册根 + 盘符顶层）——后者的本质就是注册新位置，严格 jail 会把合法功能 403 掉，且其直接效果仅是读目录列表或写 settings.json，真正的文件变更仍走 Sync Plan 预览确认 | web-server verifier 在 TCP 冒烟中发现「严格 jail 会误杀注册新路径的合法操作」；lead 裁决保留 D7 安全意图（写盘操作不放宽）同时解开功能死锁 |
| D8 | **防 CSRF/DNS rebinding**：HTTP 层校验 `Host` 头必须是 localhost，并拒绝跨源写请求（检查 `Origin`/`Sec-Fetch-Site`） | vibe-coding 开始前澄清时补充：仅监听 localhost ≠ 只有本机进程能访问，浏览器内任意网页都能向 127.0.0.1 发请求；对能删文件的无认证服务必须堵上，成本仅一个中间件 |

## 5. 风险与护栏

| 风险 | 等级 | 护栏 |
| --- | --- | --- |
| 误绑 0.0.0.0 导致无认证服务暴露公网（可远程写磁盘） | **高** | D4：非 localhost 拒绝启动；部署文档显式教 SSH 隧道 / 反代加认证 |
| 浏览器内恶意网页向 127.0.0.1 发请求（CSRF/DNS rebinding）驱动本服务 | **高** | D8：Host 头校验 + 拒绝跨源写请求 |
| HTTP 请求路径越权（删除/覆盖白名单外文件） | **高** | D7：HTTP 层统一路径白名单 jail |
| 单二进制并非 100% 自包含：更新检查依赖系统 `git` CLI（`git clone`） | 中 | 部署文档注明 git 为运行时依赖；git 缺失时更新检查功能降级报错而非崩溃 |
| `git clone <sourceUrl>` 的 URL 注入 | 低 | 现有 `normalize_github_url` 仅允许 GitHub 域名，URL 作为独立参数传递（非 shell 拼接），保留此约束 |
| 选择性摘桃随时间漂移，上游大重构后摘桃失效 | 中 | D1 保持核心文件路径稳定；每个阶段起步时评估一次上游 diff |
| 服务器访问 GitHub 拉注册表/skill 受限（网络环境） | 中 | 沿用现有 skill 来源的网络假设；设置中允许换自建/镜像仓库（原 PRD 已含） |
| 双形态长期维护两份壳的适配层 | 低 | 壳保持薄：tauri command 与 HTTP endpoint 都只是核心函数的薄转发 |

## 6. MVP 分期（最终版）

| 阶段 | 范围 |
| --- | --- |
| **阶段一：Web 壳** | axum HTTP 服务封装共享核心；invoke → fetch 适配层；rust-embed 单二进制；D3 目录浏览 API；D4 启动护栏；Linux 部署文档（含 SSH 隧道访问指南） |
| **阶段二：工作流 v1**（= 原 PRD v1） | Workflows tab；本地创建/编排（分组、一步多 skill、占位步骤）；使用工作流（复用 Sync Plan，缺失一并下载）；双输出形态（入口清单 / 打包 skill 结构化拷贝）；从 `oh-my-skills-workflows` 注册表浏览下载 |
| **阶段三：工作流 v2**（= 原 PRD v2） | 一键推送 / fork+PR 贡献；私有/团队仓库（token 存储）；工作流版本/哈希更新检查；导出分享包 |
| **移出范围** | Docker 镜像（Q4）；可执行控制流、后端市场 API（原 PRD 非目标，继续有效） |

> **开发环境说明（2026-07-28 补充）**：开发端为 Windows。Web 壳全程可在 Windows 上开发测试——
> 依据：Rust 核心 CI 本就在 windows-latest 跑测试；axum/React/浏览器全部跨平台；
> Web 版语义就是「监听 localhost + 浏览器访问」，与宿主 OS 无关。
> 仅最终 Linux 部署验证（systemd、部署文档走查）需要真实 Linux 环境（WSL2 或目标服务器）。
