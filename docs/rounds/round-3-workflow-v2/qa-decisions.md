## Q1 · 导出分享包是否需要配套导入（2026-07-29 拍板）

**背景**：PRD 只说「导出分享包自行推送」，没回答分享包的消费方是谁。若面向「不走 git 的人」，导出-only 是死产物。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| 仅导出，消费走注册表 | 导出 zip 仅作「自行推送」载体；消费侧 = v1 已有的注册表下载 |
| 导出 + 应用内导入 | 新增「导入分享包」（选 zip → 校验 → 装为本地工作流），覆盖人肉传包场景 |
| 导出即打包 skill 包 | 导出打包 skill 形态 zip，接收方直接放 agent skills 目录，不经本应用 |

**推荐**：仅导出（范围最小，符合 PRD 字面）。

**谁拍**：用户。

**✅ 最终选择**：**导出 + 应用内导入**——「按做产品的思维，有导出就有导入」。导入面向个人本地实例。

**备注**：导入带来新安全面（恶意 zip / 路径穿越 / zip 炸弹），详细设计必须含校验红线。

## Q2 · 公共中心形态（2026-07-29 拍板）

**背景**：用户提出「部署到服务器上供广大网友使用的版本」如何落地。第一次澄清时用户表示「我不知道如何处理这种情况，你给一些建议」，lead 给出分析后用户明确拍板。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| GitHub 仓库即公共中心 | 不部署公共 app；网友在 GitHub 网页浏览/提 PR，本地实例经注册表拉取（lead 推荐） |
| 推荐项 + GitHub Pages 静态展示页 | 同上，另加纯静态浏览页（后续轮） |
| 公共服务器版 | 真部署一套程序到云端 + 域名，访客直接访问下载 |

**推荐**：GitHub 仓库即公共中心（零新增服务端、不触红线）。

**谁拍**：用户（第二次确认时给出了完整产品愿景描述）。

**✅ 最终选择**：**公共服务器版，但不需要多租户**——用户原话要点：
- 最终把这套程序部署到云端 + 域名，大家都可以访问、下载分享的 skill/工作流
- 不需要多租户：访客无账号、无个人库，看的是同一份中心内容
- 贡献通道：网友提 PR → 审核合并 → 纳入分享
- 想本地自用的网友：fork 或下载源码自行部署

**红线影响（lead 分析，用户已知悉）**：
- 该愿景里访客是**只读**的 → 落地必须配「访客只读模式」新护栏（公网部署关闭全部写端点），否则现有 D4 防的正是「无认证写端点暴露公网 = 任何人可远程删文件」
- 不推翻 Q3 精神（无多租户成立），但要**修订 Q6/D4 字面约束**（允许公网绑定 + 强制只读）
- 内容源头仍是 GitHub 注册表仓库（PR 审核在 GitHub 做）；公共服务器 = 拉齐注册表内容 + 只读窗口的实例；**v2 的版本更新检查 = 公共服务器内容保鲜机制**
- skill 的 PR 式分享需要自己的 skill 注册表仓库（现状 skill 来源是外部 skills.sh）——列入开放问题，不在本轮

**落地分期**：见 Q3（并入本轮）。

## Q4 · 私有仓库 token 本地存储方式（2026-07-29 拍板，安全红线）

**背景**：QA 决策文档 §8 遗留开放问题。调研实证：OS keyring 在 headless Linux 不可行（Secret Service 需 D-Bus session + keyring provider，均缺）；Windows 桌面可用 WCM，但双形态分叉 + 新依赖。现有错误消息直拼 URL，token 嵌入 URL 会泄漏。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| settings.json 明文 + 缓解 + env 优先（推荐） | UI 密码框掩码、错误/日志全链路脱敏、文件 0600 权限（unix）；OMS_GITHUB_TOKEN 环境变量优先覆盖。与 gh CLI 默认同级，双壳零分叉零新依赖 |
| 桌面 keyring + headless 文件/env | 桌面更安全，但双形态分叉 + keyring 依赖；headless 上 keyring 本就不可用 |
| 仅环境变量 | 最安全；桌面用户体验差 |

**✅ 最终选择**：**settings.json 明文 + 三重缓解 + OMS_GITHUB_TOKEN 环境变量优先**。

**配套红线（设计必须落实）**：① token 永不出现在错误消息/日志/前端普通文本（仅掩码）；② save_settings 等返回体不回传明文 token（回传是否已配置）；③ git 调用凭证注入走 `-c http.extraheader`（不进 URL、不进命令行参数表 ps 可见面——extraheader 经 -c 会进进程参数，设计评审需复核 Windows 下本机可见性可接受）。

## Q5 · 个人实例「一键贡献」自动化程度（2026-07-29 拍板）

**背景**：用户提出站内「上传贡献」替代原 PRD 的 fork+PR 引导。调研实证：GitHub fork API 异步（需轮询就绪）；fine-grained PAT 无法跨 owner 建 PR（需 classic PAT）；本机 git 有 GCM 弹窗风险（须 GIT_TERMINAL_PROMPT=0）。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| 自动到 PR 预览页（推荐） | token 推送分支到用户 fork（无 fork 先自动打开 fork 页）→ 自动打开预填 compare URL，用户点 Create。零新依赖、fine-grained PAT 即可、最后一步人工确认 = 贡献者自检 |
| 全自动 API 建 PR | 零点击，但需 classic PAT + HTTP 客户端新依赖 + fork 异步轮询 |
| 零 token 手动引导 | 导出包 + 打开 fork 页 + 图文引导 |

**✅ 最终选择**：**自动到 PR 预览页**；零 token 降级（导出包 + 引导）作为无 token 时的兜底路径保留。

**备注**：公共服务器（访客上传）用运营者 bot token，对自己的注册表仓库有写权限，无需 fork、无需跨 owner——服务端全自动建 PR（gh CLI 或 HTTP API，设计期选型），与个人实例路径不同。

## Q6 · 导出分享包内容契约（2026-07-29 拍板）

**背景**：瘦包（yaml+README+来源元数据，skill 用时现拉）vs 胖包（含全部引用 skill）。lead 原推荐瘦包。

**✅ 最终选择**：**胖包（含全部 skill）** —— 用户拍板。落地后自洽逻辑：胖包是公共站访客的下载载体，自包含、解压即用，消费方不需要本应用也不需要逐个拉取 skill。

**设计影响**：导出需联网抓取 steps 引用的全部 skill（复用 skill_ops checkout）；失败语义（部分 skill 拉取失败 → 报错并列出，不产半成品包）；与「打包 skill」输出形态的关系需在详细设计厘清（胖包 ≈ 打包 skill + workflow.yaml + README + 来源元数据 的可传输 zip）。

## Q7 · 更新检查对「本地已修改」的策略（2026-07-29 拍板）

**背景**：调研 critic 一号缺口——工作流可被本地编辑（skill 不行），hash 比对会把本地修改误报为「永久有更新」，「备份-删-重建」会静默吞掉本地修改；且本地自创与注册表下载混存于同一 workflows/ 命名空间、无来源标记。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| 三态 + 确认后备份覆盖（推荐） | 下载时写来源元数据（registry URL + path + 下载时哈希）。未修改 → 可一键更新（先备份）；已修改 → 标「已修改」，更新需显式确认且先备份；本地自创 → 不参与更新检查 |
| 已修改禁止更新 | 只能手动删除重下，最安全体验最差 |
| 静默覆盖（skill 语义） | 最简单但吞本地修改，critic 点名的返工源 |

**✅ 最终选择**：**三态 + 确认后备份覆盖**。

## Q8 · skill 贡献与分发范围（2026-07-29 拍板）

**背景**：用户两次明确贡献物包含 skill，但 skill 现状全部来自外部源（skills.sh 等），无自有 skill 注册表仓库。skill 注册表 = 建仓 + app 认它为来源 + 浏览下载 + 贡献上传 ≈ 再造一个 registry-client。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| 本轮仅工作流贡献（lead 推荐） | skill 注册表列入开放问题下轮做；本轮已含公共部署，体量到顶 |
| 本轮含 skill 注册表全链路 | 建 Pgooone/oh-my-skills-skills + 贡献上传 + 浏览下载 |
| 只建仓 + 贡献 | 贡献物暂无消费方 |

**✅ 最终选择**：**本轮含 skill 注册表全链路** —— 用户拍板。lead 备注：本轮体量已达 7 个功能块，实现批次将把 skill 注册表排在后段（独立性最高），若门禁/验收风险累积，用户可选择将其切分为 R3.5 而不影响前六块收官。

**设计红利（调研发现；设计评审门后修订）**：原表述「skill 注册表下载写 lock 条目后，现有 check_skills_sh_update 原生接管更新检查」经评审门承重反驳**部分证伪**（2026-07-29）：Rust 函数层成立（check 无路径守卫、中心库 jail 放行），但**前端触发链不存在**——skillsShInstallationCandidate 结构性排除中心库安装、refreshSkillsShUpdateChecks 全 src 无调用点（死代码）。修订后语义：**Rust check 函数复用 + 前端触发链新增两处小改**（候选兜底 + refreshInventory 后触发），另补同 slug 异源冲突拒绝、byte-verbatim 下载约束。详见 design-review.md B6/L1-L3。
